## What this project is

AOBench (Agent Operations Benchmark) is an open-source Python benchmark framework for
evaluating AI agents that operate High-Performance Computing systems — job scheduling,
telemetry interpretation, energy reasoning, policy enforcement. Agents are evaluated
against **deterministic environment snapshots** with mock HPC tools (SLURM, telemetry,
docs, RBAC, facility), never against live clusters, so every result is reproducible and
safe to publish.

Python ≥ 3.10 (3.12 in CI and Docker). Package manager and runner: **`uv`**.

## Architecture in brief

| Path | Contains |
|---|---|
| `src/aobench/adapters/` | `BaseAdapter.run(context) -> Trace` — one per agent backend |
| `src/aobench/scorers/` | `BaseScorer.score(task, trace) -> ScorerOutput`; `AggregateScorer` combines them |
| `src/aobench/schemas/` | Pydantic models — `TaskSpec`, `Trace`, `BenchmarkResult`, `EnvironmentSnapshot` |
| `src/aobench/tools/` | Mock HPC tool families; `ToolRegistry` filters them by role |
| `src/aobench/cli/` | Typer CLI, one module per command group |
| `src/aobench/reports/` | Report renderers, CLEAR scorecard |
| `benchmark/tasks/specs/` | Task specs, one JSON file each |
| `benchmark/environments/` | Environment snapshot bundles |
| `tests/` | `unit/`, `integration/`, `runners/`, `scripts/`, `cli/` |
| `docs/` | User-facing documentation (MkDocs) |
| `examples/` | Runnable examples — all run offline with no API key |

Execution flow: CLI → `BenchmarkRunner.run(task_id, env_id)` → load `TaskSpec` + snapshot →
`build_tool_registry(env, role, allowed_tools)` → `adapter.run(context) -> Trace` →
`AggregateScorer.score(task, trace)` → persist to `data/runs/<run_id>/`.

### Invariants that must not be broken

- **Determinism.** The same task, environment, and trace must always score identically.
  Never introduce wall-clock time, randomness, or filesystem ordering into scoring.
- **No network in tests.** Unit and integration tests must pass offline with no
  credentials. Mock the provider client; never call a real endpoint.
- **Snapshots are read-only.** Tools read from the environment bundle. Nothing in
  `src/aobench/tools/` may write to `benchmark/environments/`.
- **RBAC is enforced, not advisory.** A role must never gain access to a tool that
  `rbac_policy.yaml` denies it. A `hard_fail` in `GovernanceScorer` zeroes the task score,
  and that behaviour is deliberate.
- **The `test` split is held out.** It is locked behind `AOBENCH_UNLOCK_TEST=1`. Never
  default to it, never include it in an example, and never add a task to it in a PR.
- **Traces carry token counts.** The efficiency scorer and the CLEAR cost axis depend on
  them; a trace missing them scores wrongly rather than failing loudly.

## Commands

```bash
uv sync --all-extras                      # setup — dev group + all optional extras
uv run python -m pytest tests/            # tests (use `python -m pytest`, not bare pytest)
uv run ruff check src/ tests/             # lint
uv run ruff format src/ tests/            # format
uv run mypy src/aobench/                  # type check (currently advisory in CI)
uv run aobench validate benchmark         # validate all task specs and environments
make check                                # lint + typecheck + tests, as CI runs them
```

Smoke check that needs no API key:

```bash
uv run aobench run task --task JOB_USR_001 --env env_01 --adapter direct_qa
```

`make check` must pass before a PR is opened. It is what CI runs.

## Conventions

- **Style is enforced by `ruff`.** Run the formatter; do not hand-format.
- **Typing:** prefer real annotations to `Any`. A `# type: ignore` requires a specific
  error code *and* a reason comment. An unexplained `Any` is debt moved, not paid.
- **Tests:** pytest, one behaviour per test, deterministic, offline. New behaviour needs a
  test in the same PR.
- **Commit messages:** `<type>(<scope>): <summary>` — e.g. `fix(cli): …`, `feat(scorers): …`.
- **Changelog:** add an entry to `CHANGELOG.md` for anything user-visible.
- **Errors:** user-facing CLI errors must be one actionable line naming the fix, not a
  traceback. See `src/aobench/cli/` for the established pattern.
- **PR size:** prefer under ~300 changed lines. Split larger work.

## Do not change

- **Generated files.** `docs/reference/task-catalog.md` and
  `docs/reference/environment-catalog.md` are generated by `scripts/gen_catalog.py` —
  run `make catalog` after changing the corpus, never hand-edit. `make catalog-check`
  fails the build if they have drifted.
- **Scoring weights** in `benchmark/configs/scoring_profiles.yaml`. Changing a weight
  changes every published number and invalidates the leaderboard. It needs a design
  discussion and a version bump of the profile, not a PR.
- **Existing task specs and environment bundles.** Adding is welcome; editing a published
  task silently changes historical results. If a task is wrong, open an issue.
- **The public CLI surface** (command names, flag names, output shape) without an issue
  agreeing the change first. People script against it.
- **On-disk formats** in `data/runs/` without a migration path.
- **CI workflow permissions** or release configuration.
- **Dependency versions**, except through Dependabot or an explicit upgrade PR.

## Validation requirements before opening a PR

1. `make check` passes.
2. `uv run aobench validate benchmark` passes if you touched `benchmark/`.
3. Any example you changed still runs offline with no API key.
4. Docs updated in the same PR — `docs/reference/commands.md` for CLI changes,
   `CHANGELOG.md` for user-visible changes.
5. Every claim in the PR description is something you ran, not something you expect.

## If you are an agent drafting a contribution on someone's behalf

- **Verify the issue's premise before writing code.** Check that the described problem
  still exists on `main` — run the failing command, or `git cat-file -e origin/main:<path>`.
  Issues do go stale; three of ours did.
- **Do not widen the scope.** If you find an adjacent bug, mention it in the PR description
  or open a separate issue. Do not fix it in the same change.
- **Do not weaken a test to make it pass.** If a test fails, either the change is wrong or
  the test encodes a real requirement. Say which, and why.
- The human opening the PR is responsible for it and must be able to explain it in review.
  Please disclose substantial AI assistance in the PR description — it is welcome, and
  saying so costs nothing.
